# 2일차: Git 브랜치 전략 (Git Flow vs GitHub Flow)

## 1. 개요
본 문서는 프로젝트의 효율적인 버전 관리 및 협업(또는 혼자 진행 시 프로젝트 관리)을 위한 브랜치 전략인 **Git Flow**와 **GitHub Flow**의 개념을 비교 정리한 문서입니다.

---

## 2. Git Flow 전략
**Git Flow**는 고도화된 소프트웨어 프로젝트나 정기적인 배포 주기가 있는 프로젝트에 적합한 브랜치 전략입니다. 총 5가지 종류의 브랜치를 활용하여 관리합니다.

### 주요 브랜치 구성
* **`main` (`master`)**: 실제 운영 환경에 배포되는 제품 출시 버전 브랜치.
* **`develop`**: 다음 출시 버전을 개발하는 통합 개발 브랜치.
* **`feature`**: 새로운 기능 개발 또는 작업 단위별 브랜치 (`develop`에서 분기, `develop`으로 Merge).
* **`release`**: 새로운 제품 출시를 준비하는 브랜치 (버그 수정, 문서 작업 등 진행).
* **`hotfix`**: 운영 환경(`main`)에서 즉시 해결해야 하는 버그가 발생했을 때 사용하는 긴급 수정 브랜치.

### 특징 및 장단점
* **장점**: 역할별 브랜치가 확실하게 구분되어 있어 명확한 관리 체계를 유지할 수 있습니다.
* **단점**: 브랜치가 많고 흐름이 복잡하여 소규모 프로젝트나 빠른 배포 환경에서는 과도한 오버헤드가 발생할 수 있습니다.

---

## 3. GitHub Flow 전략
**GitHub Flow**는 `main` 브랜치 하나와 기능을 개발하는 `feature` 브랜치 단 두 가지만을 사용하는 단순하고 지속적인 배포(CD) 중심의 브랜치 전략입니다.

### 주요 운영 방식
1. **`main` 브랜치는 항상 배포 가능한 상태**를 유지합니다.
2. 새로운 작업은 `main` 브랜치에서 **기능별 브랜치(`feature/...`)**를 생성하여 진행합니다.
3. 작업 완료 후 GitHub에서 **Pull Request(PR)**를 생성하여 코드 리뷰 및 검토를 거칩니다.
4. 검토 및 테스트가 완료되면 `main` 브랜치로 **Merge**하고 즉시 배포합니다.

### 특징 및 장단점
* **장점**: 구조가 매우 단순하고 빠르며, 지속적 통합 및 배포(CI/CD) 환경에 매우 적합합니다.
* **단점**: `main` 브랜치가 항상 안정적인 상태여야 하므로 철저한 테스트 자동화 및 코드 관리가 요구됩니다.

---

## 4. 결론 및 본 프로젝트 전략
현재 프로젝트는 혼자 진행하며 빠른 기능 구현 및 유연한 작업 흐름이 중요하므로, 비교적 단순하고 관리가 용이한 **GitHub Flow** 방식을 채택하여 진행합니다.
